# Node SSRの危険性の説明

Node SSRは、アプリケーション内だけじゃなく、node_modulesの更新後のスレッドセーフの安全性の担保が、延々と必要になる。

もし、一つでも見落としがあると、ユーザー間の個人情報がSSRで出力される事故になる。

コミュニティで、ある程度、危険なモジュールがないか監視されているらしいけど、人力で１００％の安全性を延々と維持し続けなくてはいけなくなり、実用的ではないと思う。

特に、モジュール管理のスペシャリストがいない小規模な組織では、より一層、実用的ではないと思う。

## NodeとJavascriptのスレッドセーフの違い

Nodeは常駐するため、いろいろなユーザーのリクエストが混在し、グローバル変数や、モジュール内変数全ての状態が残り続ける。

Javascriptは、クライアントのみの状態が残り続ける。

Node SSRを使うと、NodeとJavascriptが同じコードを共有する。

## node_modulesは２種類あり、それが混在している

- 完全にサーバーのみで動くもの。
- クライアントJSで動くもの。

さらに、クライアントJSで動くものにも、２種類ある。

- Node SSRに対応しているもの。
- Node SSRに対応していないもの。

さらに、Node SSRに対応しているものでも、一筋縄ではいかない。

- Node SSRで利用して安全な書き方。
- Node SSRで利用したら危険な書き方。

さらに、Node SSRに対応していて、Node SSRで利用して安全な書き方でも、問題が起きる可能性はある。

- アップデートで、危険なコードが混入する場合。
- アップデートに伴う、関連するモジュールに、危険なコードが混入する場合。

node_modulesも完全にサーバーのみで動くものは、まともなものなら、スレッドセーフの対応はされていると思う。

ただ、Node SSRで使うモジュールは、クライアントJSで動くことを想定して作られている。

そのため、Nodeで動かすと危険なことがある。

## セキュリティホール対応

上記の理由により、セキュリティホールが見つかっても、Node SSRを利用している場合は、すぐに、パッチを当てることができない。

変更されるモジュールすべての、スレッドセーフの安全性の担保ができるまで、セキュリティホールを塞げなくなる。

## 現状

上記の通りの為、構造上、完全な解決は、ほぼ不可能だと思う。

## node_modulesアップデート時の対応手順

利用するnode_modulesの中で、Node SSRで利用されるモジュールは、関連するモジュールを含めて、すべてが対象になる。

危険なコードは、すべてのstaticな変数。

具体的には、`global.`, `globalThis.`と、モジュール内変数全て。

これらが、個人情報を経由しないかの確認がすべて必要。

もし、危険なコードがある場合は、セキュリティホールがあった場合でも、更新は不可になる。

その場合は、代替手段を探し、対応する箇所全てのコードの修正が必要になる。

### 緊急のセキュリティ対応が必要な場合の対応手順

1. 一時的にSEOをあきらめて、Node SSRを無効化する。
2. セキュリティ対応。
3. スレッドセーフの安全性の確認。
4. 安全を確認したら、Node SSRを再度有効化。

## 唯一確実な対応方法

Node SSRを使わない。
