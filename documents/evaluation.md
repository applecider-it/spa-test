# 評価

通常のアプリケーションでは、`laravel-app`, `rails-app`のような、MPA+island(Vue)までが無難。

実装例を試したり、[トレンドを追うことの限界](./trend.md)を見ればわかると思うけど、SPA的な実装（SPA, Node SSR, Node SSG）は、どうあがいても正解が見えてこない。

MPA+island(Vue)は、最初から正解にいるという感じになる。

技術的に可能と実用的は別という感じになる。

ただし、+island(Vue)がないMPAも状況次第では不正解の場合もある。

## SPA的な実装の中での評価

Node SSRには、[Node SSRの危険性](./nodessr.md)があるため、除外したほうがいいので、SPAかNode SSGだけを想定して考えてみる。

評価から、reactを除外している理由は、[技術選定の理由](./selection.md)参照。

SEOが不要な場合は、SPAだと、JSがクライアントのみになり構造がシンプルになるので、比較的管理しやすい。

SEOが必要な場合は、Node SSGになる。

Node SSGをした場合には、Astro、NuxtJSのどちらもprefetchできるので、パフォーマンスは大差なさそう。

管理画面のURLをわかりにくくしたいときは、Astro、NuxtJSはファイルベースルーティングのため、実装例のようになる。

NestJSをAPIにすることで、すべてJSで実装できるので、フルスタックエンジニアを見つけやすいかもしれない。

### SPA

#### メリット

#### デメリット

- SEO

### Node SSR

#### メリット

### Node SSG

#### メリット

- [Node SSRの危険性](./nodessr.md)がない

#### デメリット

- コスト
- SEO対策で、できることが限定的になる

### レガシーMPA

#### メリット

- コスト
- SEO

#### デメリット

- インタラクティブな実装が、困難になる

### MPA+island(Vue)のようなハイブリッドMPA

#### メリット

- コスト
- SEO
- インタラクティブな実装も可能。

#### デメリット

- インタラクティブな実装も含めると習得コストが高い。ただし、他の方法でも、全体を見る場合は同じなので、デメリットと呼べるかは微妙。


## コストの細分化

コストと言っても、いろいろある。

SPA的な実装では、複雑なためエンジニアの単価が高くなり、必要とする人材を見つけにくい。

クライアントとサーバーサイドでエンジニアを分ける場合は、エンジニア間のコミュニケーションコストが増える。

さらに、障害発生率が上昇し、原因の特定が困難になり、複雑化するためメンテナンスコストが上昇する。

Laravel, Railsだと、認証など基本的な仕組みが、システムごとで違いがなくなるため、新規参加者が慣れるまでの時間が短い。

SPA的な実装では、システムごとに異なってくるため、慣れるまでの時間がかかる。

慣れたころには、プロジェクトを離脱しているということにもなりかねない。

SPA的な実装での、コストの細分化をリストアップすると、こんな感じ。

- エンジニアの単価、見つけるコスト
- エンジニア間のコミュニケーションコスト
- 新規参加者が慣れるまでのコスト
- 障害発生率
- 障害対応時間
- ランニングコスト

コストとできることのバランスが、ハイブリッドMPAが一番無難だと思う。

## クライアントとサーバーサイドでエンジニアを分ける

SPA的な実装では、クライアントとサーバーサイドでエンジニアを分けるのは、仕方がない部分もある。

なぜなら、SPA的な実装では、クライアントとサーバーサイドでシステムが分離されるため、認知負荷が高くなるので、分けないのはしんどいから。

特に、初心者のうちは、難しいと思う。

ハイブリッドMPAだと、この認知負荷がかなり低くなる。

## エンジニア間のコミュニケーションコスト

エンジニアはコミュニケーションの適性が低い。

これは、エンジニアが悪いのではなくて、エンジニアの役割上、必然的にそうなる。（詳しくは`github-test`参照）

速い話、エンジニアという仕事は、コミュニケーションの適性が高い人ほど、不具合を起こしやすくなるようにできている。

そして、一般的には、コミュニケーションの適性が高い人はエンジニアにはならないで、営業や総務になる。

つまり、エンジニア間のコミュニケーションコストは、必然的に高くなりやすい。

エンジニア間の連帯がある場合でも、中程度、ない場合は、かなり高い状態になる。

そのため、クライアントとサーバーサイドでエンジニアを分けるときは、場合によっては、ハブとなる人がいたほうがいいと思う。

つまり、クライアントとサーバーサイドでエンジニアを分けると、そのハブとなる人のコストも増える。

## レガシーMPAが不正解になる場面

レガシーMPAは、基本的な挙動を作るだけなら、効率的。

ただし、少しでも複雑な画面を作ると、一気に難しくなる。

MPAにインタラクティブな挙動を埋め込む方法には、livewire, turbo streams, htmxなどの選択肢もある。

これらは、ある程度複雑な処理までは可能だけど、さらに、複雑な処理だと実装できなくなることがある。

そのため、最初から、アイランドアーキテクチャでvueを埋め込むのが無難だと思う。

さらに、この仕組みは、潰しがききやすい。

詳しくは、`docker-test`参照。

## 重たいSPAが抱える問題

SPA的な実装をすると、ページ遷移しても状態が残るため、クライアント側がだんだんと重くなってくる。

PCだと、あまり影響を感じないけど、モバイル端末だと、動作がどんどん重たくなる。

弱い端末の場合は、最初から、ほとんど動かない場合もある。
